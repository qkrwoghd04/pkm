#### 품질 요구사항

시스템은 중복 클릭·재시도·동시 요청이 발생해도 핵심 업무 데이터를 중복 생성하거나 일부만 저장하거나 허용되지 않은 상태로 변경하지 않아야 합니다.

#### 목적·영향

중복 신청·중복 견적·복수 최종 선택과 부분 저장은 고객·파트너·공급업체 간 업무 결과를 서로 다르게 만들 수 있으므로, 핵심 상태 변경의 단일성과 추적성을 보장합니다.

#### 적용 조건

- 환경: 운영·검증 환경
- 적용 시점: 생성·확정·상태 변경 요청과 동일 요청 재전송·동시 처리 시
- 제외 조건: 읽기 전용 조회와 명시적으로 복수 생성을 허용한 기준정보

#### 기준 미충족·예외 처리

- 미충족 시 처리: 중복·복수 확정·부분 저장은 출시 차단 결함으로 처리. 운영 중 발견 시 추가 변경을 중지하고 원본 로그 보존 후 복구
- 예외 허용 조건: 업무 규칙상 복수 활성값이 명시적으로 허용되고 FR·상태 정의에 근거가 있는 경우
- 예외 승인 주체·기한: 기획 책임자와 개발 책임자 공동 승인 / 해당 기능 배포 전

#### 검증·수용 기준

- Given: 동일 업무 대상을 처리할 수 있는 두 계정과 유효한 이전 상태가 준비되어 있음
- When: 동일 버튼 연속 클릭, 동일 API 재전송, 두 사용자의 동시 상태 변경을 수행함
- Then: 하나의 유효한 결과만 남고 부분 저장·허용되지 않은 상태 전이가 발생하지 않으며 변경 이력이 기록됨
- 검증 근거: 중복·동시성·트랜잭션 테스트 결과, 변경 이력 표본
